# 타자 성경통독(Reading) 설계 (2026-07-27)

`verse-flutter`에 두 번째 코어 루프를 추가한다: 절 텍스트를 보면서 타이핑으로
따라 치는 성경통독. 암송(고강도·하트 소모·채점)과 대등한 트랙으로,
플랜 시스템을 공유하되 진행 기록·성취·수익화는 분리한다.

**전제:** 이 스펙은 `2026-07-27-plan-management-design.md`(플랜 포기/변경·섹션
범위 선택)가 구현 완료된 코드베이스를 가정한다. 통독 플랜은 그 플랜 레일에
`mode` 하나를 얹는 것이다.

## 왜 이 기능인가

- 콘텐츠가 이미 있다. 구약 39권·신약 27권 코스에 KJV 전체 절이 적재되어 있다
  (창세기 1,533절 전부). 통독은 새 콘텐츠 파이프라인이 필요 없다.
- 암송은 하드코어 소수의 습관이지만 통독·필사는 주류 실천이다. 실패 없는
  저강도 루프가 생기면 "오늘은 지쳤으니 통독만" 하는 날에도 스트릭이 이어진다.
- 세션이 길어(영어 한 장 10~20분) 체류시간 기반 수익화가 암송보다 안정적이다.

## 결정 사항 (브레인스토밍 합의)

1. 타이핑 텍스트는 **KJV 영어 원문**. 기존 데이터 그대로 — 한글 성경 적재는 제외.
2. 오타는 **맞게 칠 때까지 대기**. 틀린 글자는 빨간 표시 + 커서 정지, 맞는 키를
   치면 진행. 항상 정확한 텍스트가 완성된다.
3. 성취는 **픽셀 성경책장** — 66권 그리드, 장을 칠수록 책이 차오르고 완독 시 꽂힘.
4. 책장 위치는 **카드 탭을 세그먼트로 확장**(`[카드 | 책장]`). 탭 구조 변경 없음.
5. 광고는 **절 경계 + 5분 간격** 전면광고만. 보상형은 제외.
6. 플랫폼은 **Flutter 모바일만**. 웹 이식은 검증 후.
7. 암송·통독 플랜은 **완전 대칭** — 각자 생성·변경·포기·마감 수정 모두 가능.
8. **통독 진행은 서버 동기화한다** — 재설치/기기 변경 시 책장이 복원되어야 한다.

## 1. 데이터 모델

### 1.1 플랜에 mode 추가 (drift)

`memorization_plan`에 컬럼 하나:

```dart
TextColumn get mode => text().withDefault(const Constant('memorize'))(); // memorize|reading
```

- `PlanRepository.activePlan({String mode = 'memorize'})` — 모드별로 조회.
- **모드별 활성 플랜 1개씩**. 암송 1 + 통독 1 동시 진행이 최대이며, 같은 모드로
  두 개는 만들 수 없다(새로 만들면 기존 것을 변경/포기 플로우로 정리).
- `planView(mode)`도 동일하게 분기. `activePlanViewProvider`는
  `memorizePlanViewProvider` / `readingPlanViewProvider` 두 개로 나뉜다.

### 1.2 통독 진행 (drift, 신규 테이블)

```dart
class ReadingProgress extends Table {
  IntColumn get courseItemId => integer()();
  DateTimeColumn get typedAt => dateTime()();
  TextColumn get syncStatus => text().withDefault(const Constant('pending'))(); // pending|synced

  @override
  Set<Column> get primaryKey => {courseItemId};
}
```

**암송 `progress`와 절대 섞지 않는다.** `progress.cleared`는 "외웠다"는 뜻이고
카드 보상·랭킹 점수·암송 통계의 근거다. 통독으로 타이핑한 절을 cleared 처리하면
그 지표가 전부 오염된다. 통독 플랜의 진행률은 `reading_progress`만 센다.

**스트릭은 공유한다.** 어느 트랙이든 하루에 활동하면 스트릭이 이어진다 —
리텐션 자산은 통합, 성취 자산은 분리가 원칙이다.

### 1.3 서버 (verse-backend)

마이그레이션 `000019_reading_progress`:

```sql
CREATE TABLE reading_progress (
  id             BIGSERIAL PRIMARY KEY,
  user_id        BIGINT NOT NULL REFERENCES users(id),
  course_item_id BIGINT NOT NULL REFERENCES course_items(id),
  typed_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE(user_id, course_item_id)
);
```

엔드포인트 2개(인증 필요, 기존 미들웨어 재사용):

- `POST /sync/reading` — 배치 업서트. 요청 `{"items":[{"course_item_id":N,"typed_at":"..."}]}`,
  응답 `{"synced":N}`. 중복은 `ON CONFLICT DO NOTHING`(첫 타이핑 시각을 보존).
- `GET /sync/reading` — 사용자의 전체 통독 진행 목록. 재설치 복원용.

### 1.4 동기화 (모바일)

기존 `SyncService.syncPendingAttempts`의 오프라인 우선 배치 패턴을 그대로 따른다:

- 통독 절 완료 → `reading_progress`에 `pending`으로 로컬 기록(즉시 UI 반영).
- `syncPendingReading()` — pending 행을 청크로 묶어 `POST /sync/reading`, 성공분만
  `synced` 표시. offline/unauthorized면 중단하고 다음 트리거 때 이어서 시도.
- 비로그인 사용자는 로컬에만 쌓인다(암송과 동일). 로그인 시 전량 업로드.
- 로그인 직후 1회 `GET /sync/reading`으로 서버 기록을 로컬에 병합(없는 것만 삽입).

**플랜 자체는 로컬 전용으로 남긴다** — 암송 플랜도 현재 로컬 전용이라 일관된다.
동기화 대상은 진행 기록뿐이다.

## 2. 플랜 생성 — 트랙 갈림길

플랜 관리 스펙의 생성 화면 1단계 **앞에** 갈림길 하나를 추가한다:

```
어떻게 할까요?
[🧠 암송 — 외우고 채점받기]   [⌨️ 통독 — 보고 따라 치기]
```

이후 단계는 **전부 재사용**한다: 범위 선택(권 → 장 칩, 기본 1장), 마감(프리셋 +
직접 선택), 하루 절수 미리보기. 차이는 하나뿐 — 통독은 성경 책 경로만 노출한다
(소형 코스·워밍업 섹터는 암송 전용 큐레이션이다).

생성 시 `createPlan(mode: 'reading', ...)`.

## 3. Today 투트랙

플랜 카드를 두 장 스택으로:

- 암송 플랜 카드(기존) + 통독 플랜 카드. 각자 라벨·진행바·D-day·"이어서" CTA.
- 두 카드 모두 **탭하면 같은 플랜 관리 바텀시트**(마감 변경/플랜 변경/플랜 포기).
  통독 플랜을 포기해도 통독 진행 기록은 남는다(암송과 동일 원칙).
- 카드가 하나도 없으면 기존 빈 상태, 하나만 있으면 그 카드 + 다른 트랙을
  시작하는 작은 링크("통독도 시작하기").
- 오늘 목표는 트랙별로 계산하고 각 카드에 표시한다.
- 마스코트 무드: **둘 중 하나라도 오늘치 완료면 happy**. 저강도 유저도 매일
  성공 경험을 가져가게 한다.

## 4. 통독 화면 (신규)

`lib/features/reading/reading_screen.dart`. 암송 화면(`memorize_screen.dart`)을
재사용하지 않는다 — 목적이 정반대다(긴장 vs 몰입).

- 상단: 절 참조(예: `Genesis 1:3`) + 장 진행("12/31절").
- 본문: 절 원문을 크게 표시. 이미 친 부분은 확정 색, 현재 위치는 커서 강조,
  아직 안 친 부분은 흐리게.
- 입력: 화면 하단 텍스트 필드(모바일 키보드). 한 글자씩 대조한다.
  - 맞으면 커서 전진.
  - **틀리면 커서 정지 + 그 글자 빨간 표시.** 맞는 키를 칠 때까지 진행하지 않는다.
    백스페이스는 허용(직전 글자 취소).
- 절을 다 치면: 짧은 확인 피드백 → `reading_progress` 기록 → 자동으로 다음 절.
- 장을 다 치면: 장 완료 축하 화면(책장에 한 칸 차오르는 연출) → 다음 장 또는 종료.
- **하트·채점·재도전 없음.** 하트 배지도 이 화면에는 띄우지 않는다.
- 사운드/햅틱은 기존 `Sfx` 설정을 따른다(오타 시 짧은 진동 정도).

## 5. 픽셀 성경책장

카드 탭 상단에 세그먼트 `[카드 | 책장]`을 추가한다(탭 구조·라우트 변경 없음).

- 책장 뷰: 66권을 픽셀 책 스프라이트 그리드로. 각 책의 채움 정도 =
  `그 코스에서 reading_progress에 있는 절 / 전체 절`.
- 미착수는 흐린 실루엣, 진행 중은 부분 채움, 완독은 선명한 책 + 꽂힘 연출.
- 책을 탭하면 장별 진행(장 칩 그리드에 완료 표시) — 플랜 생성의 장 칩 UI와
  동일한 시각 언어를 쓴다.
- 구약/신약 구분은 그리드 섹션 헤더로.

## 6. 광고

**규칙: 절(節) 경계에서만, 마지막 광고 후 5분 이상 지났을 때 전면광고 1회.**

- 절을 치는 도중에는 절대 띄우지 않는다. 몰입이 통독의 상품성이고, 작업 중간
  강제 노출은 AdMob 정책상으로도 문제가 된다.
- 장 완료 축하 화면도 절 경계이므로 자연히 포함된다.
- 간격(5분)과 일일 상한은 상수 하나로 빼서 나중에 조정만 하면 되게 한다.
- **첫 장은 광고 면제** — 첫 경험에서 광고를 만나면 이탈한다.
- 영어 한 장이 10~20분이라 이 규칙이면 장당 2~3회 노출된다.

**선행 조건:** 전면광고 도입 전에 광고 빈도 제어·UMP 동의폼 작업이 끝나야 한다
(`docs/admob-monetization-status-2026-07-17.md`에 미완으로 기록됨).

**구독 연결:** 전면광고를 정기적으로 보는 통독 유저가 "광고 제거" 구독의 최우선
전환 대상이다(`docs/subscription-implementation-plan.md`). 통독은 광고 수익원이자
구독 퍼널이다.

## 7. 오류·엣지 케이스

- **절 텍스트에 특수문자**: KJV에는 이탤릭 표기·구두점이 있다. 대조는 정규화된
  형태(연속 공백 1개로, 유니코드 따옴표를 ASCII로)로 하되 화면 표시는 원문 그대로.
- **매우 긴 절**: 시편 119편 등. 절 안에서도 스크롤이 따라가야 한다(커서가 항상
  화면 안에 보이도록 auto-scroll).
- **이미 통독한 절을 다시 침**: `typed_at`을 갱신하지 않는다(첫 완료 시각 보존).
  진행률은 변하지 않고, 다시 치는 것 자체는 허용한다.
- **오프라인**: 전부 로컬로 동작한다. 동기화 실패는 Today의 기존 동기화 배너로
  알린다(암송과 같은 배너 재사용).
- **비로그인 사용자**: 로컬에만 쌓이고 책장도 정상 동작한다. 재설치 시 유실되며,
  이는 로그인을 권하는 지점이다(강제하지 않는다).

## 8. 테스트

- 통독 진행 저장소: 기록/중복 무시/코스별 집계, `progress`와 독립임을 검증.
- 동기화: pending 배치 업로드, offline/unauthorized 시 중단·재시도, 서버 병합.
- 타이핑 대조 로직(순수 함수): 정타 전진, 오타 정지, 백스페이스, 정규화.
- 광고 게이트(순수 함수): 5분 미만이면 false, 절 경계 아니면 false, 첫 장 면제.
- 위젯: 투트랙 Today 카드 2장, 통독 화면 오타 정지 표시, 책장 채움 비율.
- 백엔드: `POST/GET /sync/reading` 핸들러 + 마이그레이션 up/down.

## 9. 구현 단계 분할

이 스펙은 하나의 구현 계획으로 삼기엔 크다(모바일 코어 + 백엔드 + 수익화).
아래 3단계로 나눠 각 단계가 **그 자체로 동작하는 소프트웨어**가 되게 한다.
각 단계는 별도 계획 문서를 갖는다.

**Phase A — 통독 코어 (로컬 전용)**
§1.1 mode 컬럼, §1.2 reading_progress 로컬 테이블, §2 트랙 갈림길,
§3 투트랙 Today, §4 통독 화면. 이 단계만으로 통독이 완전히 동작한다(오프라인).

**Phase B — 책장 + 서버 동기화**
§5 픽셀 성경책장, §1.3 백엔드 마이그레이션·엔드포인트, §1.4 동기화·복원.
책장이 생겨야 동기화 복원의 가치가 눈에 보이므로 함께 간다.

**Phase C — 수익화**
§6 광고. 선행 조건(UMP 동의폼·빈도 제어)이 끝난 뒤에 착수한다.

## 10. 범위 제외

- 한글 성경 데이터 적재(별도 프로젝트)
- 웹(verse-web-next) 이식 — 모바일 검증 후
- 플랜 자체의 서버 동기화(암송 플랜도 로컬 전용)
- 보상형 광고, 책장 꾸미기 요소
- 통독 랭킹·카드 보상(암송 전용으로 유지)
- 통독 전용 알림(기존 리마인더 재사용)
